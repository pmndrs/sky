Aerial-perspective ("AP") haze is what makes distant geometry desaturate
and blue-shift with distance, the way a real atmosphere does. It's an
opt-in post-process on your scene's opaque geometry — the sky background
itself already includes atmospheric scattering via the Sky-View LUT; haze
is specifically about _surfaces_ under that same atmosphere.

For a cheaper look with no per-frame LUT, see
[Height fog](#height-fog-the-budget-tier) (`applyFog`) at the end of this page.

## Enabling it

```js
const sky = new Sky(renderer, {
  preset: 'earth',
  enableAerialPerspective: true, // default; must be true to use applyHaze
})
```

## Wiring the post-process

```js
import { pass } from 'three/tsl'

const scenePass = pass(scene, camera)
const post = new THREE.RenderPipeline(renderer)
post.outputNode = sky.applyHaze(scenePass.getTextureNode(), {
  scenePass,
  policy: 'auto', // 'auto' | 'ap' | 'raymarch'
  strength: 1.0,
})

renderer.setAnimationLoop(() => {
  sky.update(camera)
  sky.updateAerialPerspective() // must run every frame — camera-dependent LUT
  post.render()
})
```

`sky.applyHaze(...)` is a thin wrapper over the lower-level
`applyHaze(sceneColorNode, { sky, ...options })` function
(`import { applyHaze } from '@pmndrs/sky'`), which itself builds a TSL
output node via `createHazeOutputNode` (`src/sky/HazePostProcess.ts`). Use
the free function directly if you're not going through a `Sky` instance.

`updateAerialPerspective()` is separate from `sky.update()` because the AP
LUT's froxels are camera-transform-dependent and must refresh every frame,
independent of the dirty-flag system that governs the sky LUTs — see
[Baker: dirty-flag semantics](../api/baker#dirty-flag-semantics).

## Composing with other effects (bloom, AO, grading)

The first argument to `applyHaze` is the **composite base**: haze is applied
over whatever node you pass, so effects that should sit _under_ the haze
(bloom, AO, color work) must be composed into that node first. Any vec4
screen-space TSL expression works, not just a raw pass texture node:

```js
import { bloom } from 'three/examples/jsm/tsl/display/BloomNode.js'

const color = scenePass.getTextureNode('output')
const emissive = scenePass.getTextureNode('emissive')

let graph = color.add(bloom(emissive, 0.5, 0.5))
graph = sky.applyHaze(graph, { scenePass }) // haze over scene + bloom
post.outputNode = graph // temporal resolve (TRAA/FSR) goes after this
```

Sky pixels keep the base color (the cube background already contains
atmospheric scattering), so bloom that spills over the sky survives too.
The one exception is [light shafts](#light-shafts-shadowed-haze): with
`shadows` on, the shadowed in-scatter is subtracted from sky pixels as well.

> **History:** before 2026-08-09 `applyHaze` ignored `sceneColorNode` and
> composited over `scenePass.getTextureNode('output')` directly, silently
> discarding anything composed before it — the documented composition
> pattern above did not work. If haze appears to "eat" your bloom/AO, you
> are on a build older than that fix.

## Two integration methods, one output

Haze on a given geometry pixel can come from either of two integrations,
selected per-pixel by **policy**:

- **AP LUT** — samples the pre-baked 32×32×32 aerial-perspective froxel
  volume (see [LUTs](../api/luts)). Very cheap, but the volume only covers
  `kmPerSlice × 32` km of camera-relative depth (256 km by default) and is
  built assuming the camera sits inside the atmosphere looking roughly
  toward the ground.
- **Raymarch fallback** — integrates `integrateScatteredLuminance` directly
  per pixel (same function the Sky-View LUT itself uses to bake). More
  expensive per-pixel, but has no coverage limit and stays correct at any
  camera altitude/orientation.

Sky pixels never take either path — the sky mesh already renders the full
Sky-View LUT integration behind the geometry, so the post-process passes
their colour through (minus shafts, when `shadows` is on). The raymarch
fallback runs at 64 samples per pixel by default (band-free on 1000 km
grazing rays at orbit altitude); ground-level scenes whose raymarched
geometry stays close can cheapen the shader with
`applyHaze(node, { raymarchSampleCount: 32 })`.
This is a build-time constant, not a live uniform — call `applyHaze`
again to change it.

Scenes whose geometry never exceeds AP coverage (a city under the default
256 km cap) can drop the fallback from the shader entirely with
`applyHaze(node, { raymarchFallback: false })` — the haze node shrinks to
a LUT sample + composite, which compiles dramatically faster inside large
post-processing megashaders (bloom + AO + temporal resolve). With it off,
`policy: 'raymarch'` and the altitude blend are inert.

### `policy` options

| Policy             | Behavior                                                                                                                                                                                                                                                                                       |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `'auto'` (default) | Blends AP → raymarch by two independent weights, taking the max: **altitude** (`smoothstep` between `altitudeBlend.startKm`/`endKm`, default 50/100 km) and **coverage** (geometry past the AP LUT's total range always gets raymarched, blended in over the last `128` km before the cutoff). |
| `'ap'`             | AP-first — only falls back to raymarch for geometry beyond the LUT's coverage distance.                                                                                                                                                                                                        |
| `'raymarch'`       | Force raymarch for every geometry pixel, unconditionally. No LUT coverage limit, but costs a full per-pixel integration everywhere haze is visible.                                                                                                                                            |

Switch policy live without rebuilding the pipeline:

```js
sky.setHazePolicy('raymarch')
```

### Altitude blend window (`'auto'` policy only)

```js
sky.setHazeAltitudeBlend({ startKm: 50, endKm: 100 })
```

Below `startKm` altitude, the AP LUT is used; above `endKm`, raymarch is
fully active; smoothstep between. Tune this window for your scene's
altitude range — a ground-level scene never needs to touch it (well below
`startKm` by default), while planet-scale scenes (see the
[Planet-scale guide](../guides/planet-scale)) may want to shift or narrow
it. `component-03-planet.html` exposes `blendStartKm`/`blendEndKm` sliders.

## Coverage: `apKmPerSlice`

The AP LUT's total camera-relative coverage is `apKmPerSlice × 32` km
(32 slices, fixed). The default `apKmPerSlice: 8.0` gives 256 km coverage,
tuned for ground-level demos. Planet-scale scenes that need to see haze
from further out should raise it:

```js
const sky = new Sky(renderer, {
  enableAerialPerspective: true,
  apKmPerSlice: 32.0, // 1024 km coverage
})
```

Whatever value you pass here is threaded through automatically to
`applyHaze` when you go through `sky.applyHaze(...)` — no separate
argument to keep in sync.

## `strength`

```js
sky.setHazeStrength(0.6) // 0 = no haze, 1 = physical default, >1 = exaggerated
```

Multiplies both the inscatter colour and the AP alpha (surface-occlusion)
term. Useful as an art-direction knob independent of the physical
atmosphere parameters.

## Setting knobs before `applyHaze`

The haze setters on `Sky` — `setHazeStrength`, `setHazePolicy`,
`setHazeAltitudeBlend`, `setAerialPerspectiveDistanceScale` and
`setHazeShadows` — work before the post-process exists. They create the
uniforms on the sky, and `applyHaze` adopts their current values. Only an
option you actually pass to `applyHaze` (`strength`, `policy`,
`altitudeBlend`, `shadows`) overrides what a setter stored; the defaults
apply only when neither was set:

```js
sky.setHazeStrength(0.6).setHazePolicy('ap') // e.g. restored from saved settings
post.outputNode = sky.applyHaze(color, { scenePass }) // starts at 0.6, 'ap'
```

## Light shafts (shadowed haze)

Without a shadow term every point of air glows as if the sun reached it, so
an object's shadow stops at its surface. Pass the shadow-casting light and the
haze removes the sunlight its shadow map blocks — objects then cast shafts
through the haze and against the sky:

```js
renderer.shadowMap.enabled = true
const sun = sky.createSun({ castShadow: true, shadowMapSize: 4096 })
sun.attach(scene)
sun.fitShadowToBox(new THREE.Box3(min, max)) // must enclose the *air* the shafts cross

post.outputNode = sky.applyHaze(scenePass.getTextureNode(), {
  scenePass,
  shadows: { light: sun }, // or a THREE.DirectionalLight
})

sky.setHazeShadows({ samples: 16, strength: 1.5 }) // live, no rebuild
```

| option        | default | meaning                                                                         |
| ------------- | ------- | ------------------------------------------------------------------------------- |
| `light`       | —       | `DirectionalLight` with `castShadow`, or a `SkySun`                             |
| `samples`     | `32`    | march steps per pixel inside the shadow frustum                                 |
| `maxDistance` | `20000` | metres from the camera beyond which nothing is marched                          |
| `strength`    | `1`     | multiplier on the removed light; `0` skips the march                            |
| `resolution`  | `0.5`   | march resolution vs the drawing buffer; depth-aware upsample keeps edges intact |

`sky.setHazeShadows({ light: sun })` before `applyHaze` works too: the next
`applyHaze` adopts that light and compiles the shafts in without a `shadows`
option. `shadows: false` builds a node without them even then (the stored
configuration is kept for a later call). Adding or removing the feature always
needs a new `applyHaze`; the numeric knobs stay live.

How it works: the view ray is clipped to the light's shadow frustum (an
orthographic box), marched through the shadow map with per-pixel jitter, and
the single-scattered sunlight in shadow — `T(camera→x) · σₛ·phase · T(x→sun)`
— is removed. That is the term SebH's `IntegrateScatteredLuminance` multiplies
by `getShadow`; multiple scattering stays unshadowed, as in his reference. Sky
pixels lose the absolute amount; geometry loses the same _fraction_ of its AP
in-scatter, so the result agrees with the AP LUT instead of fighting its depth
slices. Rays that never enter the frustum are untouched, and leaving `shadows`
out compiles nothing.

Things to know:

- **The frustum is the effect's extent.** Outside the shadow camera's box
  everything counts as lit, so a tight caster-only frustum gives short,
  clipped shafts. Size it to the air you want shafted; `SkySun.fitShadowToBox`
  handles the light-space fit (refit after the sun moves).
- **The shadow map must exist.** three allocates it when a lit material that
  can receive the light is compiled, and only with `renderer.shadowMap.enabled`.
  Until then the shafts are simply off; nothing errors.
- **Physical magnitude.** At `strength: 1` the removed light is the physical
  single-scattering share, so shafts are clearest looking toward a low sun
  (Mie forward peak) and over long shadowed paths. Against Bruneton's
  reference scene (1 km sphere, sun 15.5°, `20-reference-compare` view 1) the
  air in the sphere's shadow reads 0.97–1.16× his radiance with shafts on,
  1.2–2.1× without. ACES at high exposure compresses the difference — the
  `22-haze-shadows` example uses AgX 0.35.
- **Cost** (1080p, 32 samples, most of the frame inside the frustum, Apple
  GPU via headless Chromium):
  +0.6–1.1 ms at `resolution: 0.5`, +2.1–3.1 ms at `1` (spread across
  runs). It scales with the number of
  pixels whose ray enters the frustum times `samples`.
- One light, orthographic (`DirectionalLight`) shadows only; no cascades.

For `createHazeOutputNode` users wiring the post-process by hand, the shadow
state is exported:

| Export                                  | What it does                                                                 |
| --------------------------------------- | ---------------------------------------------------------------------------- |
| `HAZE_SHADOW_DEFAULTS`                  | `{ samples: 32, maxDistance: 20000, strength: 1, resolution: 0.5 }`          |
| `createHazeShadowState(options)`        | Uniform bundle for one light; pass it as `createHazeOutputNode({ shadow })`. |
| `updateHazeShadowState(state, options)` | Applies a partial options object live — what `sky.setHazeShadows` calls.     |

## Haze seen from altitude (slice refinement)

**In short:** above about 1 km, each geometry pixel fixes up its own haze so
the ground doesn't show faint rings. It's on by default, costs nothing at
ground level and about half a millisecond per frame at altitude, and you can
turn it off.

**Why it's needed.** The aerial-perspective volume stores haze at a set of
distances from the camera ("slices"), and each pixel blends between the two
slices nearest its surface. That's accurate at ground level, where haze
builds up gradually along a view ray. Seen from high up it isn't: almost all
of the haze a ray collects sits in its last few kilometres, close to the
ground, and that happens in the gap between two slices that may be tens of
kilometres apart. Blending between them gets the haze slightly wrong, by an
amount that repeats from one slice to the next, so a planet seen from above
showed faint concentric rings around the point below the camera, and the
haze read 5–13 % too light on average.

**What it does.** Above about 1 km camera altitude (fading in by 3 km), each
pixel on the aerial-perspective path takes the volume's value at the slice
just before its surface and works out the remaining stretch of its own ray
with a couple of short marches. The rings disappear and the haze matches a
full per-pixel calculation to within about 1 %.

**What it costs.** At 1920×1080 with the ground filling the screen:

| Camera                       | Extra time per frame         |
| ---------------------------- | ---------------------------- |
| On the ground (below 1 km)   | nothing measurable (skipped) |
| 25 km (an airliner and up)   | about 0.55 ms                |
| 75 km (near space, `'auto'`) | about 1–2 ms                 |

**Turning it off.** If your camera flies high and the frame budget matters
more than the rings, pass `apRefineSteps: 0`; the refinement is then left
out of the shader entirely:

```js
sky.applyHaze(sceneColor, { scenePass, apRefineSteps: 0 })
```

```jsx
<AutoHaze apRefineSteps={0} />
```

| `applyHaze` option | Default | Notes                                                                                                                              |
| ------------------ | ------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `apRefineSteps`    | `4`     | Steps in each of the two short marches. `0` turns the refinement off. Needs `raymarchFallback` (on by default). Set when building. |

## Debugging

`applyHaze`/`createHazeOutputNode` accept a `debugMode` string that swaps
the output node's return value for a diagnostic view instead of the
composited result — useful when bisecting haze issues:

`'ap-rgb'`, `'ap-alpha'`, `'w'`, `'is-sky'`, `'beyond'`, `'lin-depth'`,
`'view-z'`, `'rm-rgb'`, `'rm-alpha'`, and with `shadows` on
`'shadow-occlusion'` (fraction of march samples in shadow) and
`'shadow-deficit'` (the removed light, ×5). See `src/sky/HazePostProcess.ts` for
exactly what each mode returns — this is a debug-only surface, not a
stable part of the public API.

## `logarithmicDepthBuffer` and `useCameraFar`

If your `WebGPURenderer` was constructed with `logarithmicDepthBuffer: true`,
pass the same flag to `applyHaze` so its depth → distance reconstruction
matches:

```js
sky.applyHaze(scenePass.getTextureNode(), {
  scenePass,
  logarithmicDepthBuffer: true,
  useCameraFar: true, // see below
})
```

`useCameraFar` opts into a `viewZ`-based sky-pixel test instead of the
default linear-depth threshold. It defaults to `true` automatically when
`camera.far > 1e6` — planet-scale cameras (`camera.far` in the 10⁷ m
range) compress all real geometry into a thin sliver of `[0, 1]` linear
depth, so the default test becomes unreliable; the `viewZ` test stays
correct at any scale. See the [Planet-scale guide](../guides/planet-scale).

## Stylized looks and haze

If a [look](./looks) is assigned, AP inscatter is remapped through the same
look uniforms the sky mesh uses, chroma axis only, so haze and sky agree at
silhouettes. `setSkyLuminanceFactor` is applied to haze the same way. Nothing
to configure — `applyHaze` wires both automatically.

`setAerialPerspectiveDistanceScale(n)` (Unreal's
`AerialPerspectiveViewDistanceScale`) stretches the optical path fed into the
AP lookup: `2` is twice the haze per metre. It is a sample-time scale, so it
costs no LUT rebuild and sets no dirty flag.

## Height fog: the budget tier

`sky.applyFog` is a cheaper alternative to aerial perspective: classic
exponential height fog whose colour is the baked sky behind the geometry.
Distant terrain fades into the sky that is actually there (the sun-side glow,
the horizon gradient, twilight colours) instead of into a constant colour, and
nothing is rendered per frame for it.

```js
const sky = new Sky(renderer, { enableAerialPerspective: false }) // fog doesn't need the AP LUT
const scenePass = pass(scene, camera)
const post = new THREE.RenderPipeline(renderer)
post.outputNode = sky.applyFog(scenePass.getTextureNode(), {
  scenePass,
  density: 0.3, // per km at baseHeight
  heightFalloff: 300, // metres
})

renderer.setAnimationLoop(() => {
  sky.update(camera) // no updateAerialPerspective()
  post.render()
})

sky.setFog({ density: 1.5, baseHeight: 20 }) // live, before or after applyFog
```

### Fog or haze?

|                           | Height fog (`applyFog`)                                | Aerial perspective (`applyHaze`)                                          |
| ------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------- |
| Per-frame work            | none                                                   | AP LUT compute every frame (`updateAerialPerspective()`)                  |
| Per pixel                 | one sky-cube sample (plus a PMREM sample at night)     | one 3D LUT sample (plus the raymarch fallback past coverage)              |
| Measured cost, 1080p      | +0.09–0.10 ms by day, +0.15–0.16 ms at night           | +0.32–0.35 ms, LUT included                                               |
| Colour with distance      | veils toward the sky colour; no per-channel extinction | physical: blue in-scatter, per-channel transmittance (distant reddening)  |
| Amount                    | an art knob (`density`, `heightFalloff`)               | follows the atmosphere (`turbidity`, `setAerialPerspectiveDistanceScale`) |
| `enableAerialPerspective` | not needed                                             | required                                                                  |
| Light shafts              | no                                                     | `shadows: { light }`                                                      |
| Scale                     | local: ground fog, valley fog, a hazy city             | ground to orbit                                                           |

Use fog when the frame budget is tight, for stylised or thick weather the
physical atmosphere can't produce (valley fog, a murky city), or on top of a
scene whose sky is all you need from the library. Use haze when distant
geometry should take on the atmosphere's real colour shift, at altitude, or
with light shafts. The two compose: `sky.applyFog(sky.applyHaze(color, { scenePass }), { scenePass })`
puts a ground fog over physical aerial perspective.

Costs: whole-frame burst timing (300 frames, loop paused, waited to GPU
completion) against the same frame passing the scene through unchanged, 1920×1080, Apple GPU
via headless Chromium, minimum of 5 rounds on a machine with other GPU work
running (`examples/vanilla/scripts/verify-sky-fog.mjs`).

### Knobs

| option          | default | meaning                                                                                                                         |
| --------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `density`       | `0.3`   | Extinction per km at `baseHeight`. Visibility is about `3.9 / density` km: `0.3` is a hazy day (~13 km), `4` and up is fog.     |
| `heightFalloff` | `300`   | Scale height in metres: density drops by 1/e every `heightFalloff` metres above `baseHeight` (and grows the same way below it). |
| `baseHeight`    | `0`     | Altitude in metres where density equals `density` (world `y` on flat ground).                                                   |
| `maxOpacity`    | `1`     | Cap on the fog (Unreal `FogMaxOpacity`). Below 1 keeps distant silhouettes; `0` turns the fog off without a rebuild.            |
| `nightBlur`     | `0.4`   | PMREM roughness of the night colour (see below); `0` keeps the sharp sky at all hours. Build-time.                              |

The first four are uniforms on the `Sky`, with the same ownership rule as the
haze knobs: `sky.setFog()` works before `applyFog`, which adopts what it set,
and an option passed to `applyFog` overrides it. `logarithmicDepthBuffer` and
`debugMode` (`'fog-amount'`, `'fog-color'`, `'is-sky'`) work as for haze.

### How it works

**Opacity.** Density is `σ(h) = σ₀·e^(−(h − h₀)/H)` along the straight view
ray, so the optical depth has a closed form,

```
τ = σ₀ · d · e^(−min(a, a + x)) · (1 − e^(−|x|)) / |x|,   a = (h_cam − h₀)/H,  x = d·cosθ/H
```

with `d` the distance **along the ray** (not `|viewZ|`) and `cosθ` the ray's
vertical component. Written this way it never forms a large exponential, and
the level-ray limit (`x → 0`, where the textbook form is 0/0) is a series.
Fog opacity is `min(1 − e^(−τ), maxOpacity)`. `fogOpticalDepth` and
`fogOpacity` export the same expression on the CPU, e.g. for gameplay
visibility checks. Camera height comes from `sky.update(camera)` (world `y`,
or altitude above the sphere with `planetCenter`), and "up" is the local up,
so planet-scale scenes get fog around the camera.

**Colour.** The sky cube (`sky.texture`) along the view ray, at full
resolution: the `'fog-color'` debug view matches the background over open sky
to within one 8-bit step. Two adjustments, because the cube's lower half is
not sky (without `mirrorBelowHorizon` it is the short, nearly black air path
down to the ground; with it, a mirror of the sky):

- Rays below the horizon read the mirrored direction. The result is the same
  whichever way the cube was baked, and it is continuous at the nadir, which a
  plain clamp to the horizon is not (every azimuth would converge on the point
  straight down, swirling the sun-side and anti-sun colours round it). Most
  fogged pixels are long, near-level rays, where mirror and clamp agree.
- Samples stay one texel centre above the horizon, so filtering doesn't blend
  in the dark texels below it.

**Night.** The cube holds the baked [Milky Way](./night-sky). Sampled sharply,
it prints the galaxy's dust lanes onto fogged geometry, and thick fog makes
distant mountains look transparent. Once the sun is below −10° the fog colour
blends (fully by −16°, as the Milky Way fades in) to the PMREM-filtered sky
(`environmentTexture`) at roughness `nightBlur`, a soft glow that still
brightens toward the galaxy. Not by day: the cube has no mip chain on three
r185, and PMREM blur reaches into the dark lower half and dulls the horizon
colour (to grey at roughness 0.3–0.5 at sunset). The blend is a uniform
branch, so by day the shader pays for the one sharp sample.

Sky pixels (raw depth 1.0) pass through untouched, exactly as with haze.

What it can't do: extinction is grey, so distant objects veil but never shift
colour through the air; there is no in-scatter from the sun beyond what the
sky colour already holds; and nothing ties `density` to the atmosphere
parameters. `examples/vanilla/24-sky-fog.html` has the sliders and a
fog / haze / haze+fog / off switch on one view.
