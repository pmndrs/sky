---
title: Upgrading
description: What changes for existing scenes between @pmndrs/sky minor versions (0.3 → 0.4 → 0.5 → 0.6), and how to keep the old behaviour where you need it.
---

0.4 is mostly new features: per-frame image-based lighting, pixel-sharp stars
and the Milky Way, light shafts, a cheap sky-coloured height fog, sun colour,
a sun light that can take its brightness from the sky, compass headings in
degrees, and look-track overrides. A few defaults and behaviours changed too,
and some of them are visible in an existing scene. This page lists those, in
rough order of how likely you are to notice.

Everything here is pre-1.0, so a minor version can change behaviour; the full
list of changes is in the [changelog](https://github.com/pmndrs/sky/blob/main/CHANGELOG.md).

## 0.5 → 0.6: looks are replaced by sky grades

Looks (`setLook`, `setLookTrack`, `registerLook`, …) are removed. [Sky
grades](./sky-grades) do the same job with better results: they are keyed per
region of the dome rather than one elevation ramp, their colour swap keeps
the channel average instead of the luminance (the old one clipped saturated
targets into flat bands at sunset), and a gradient can now replace the sky
outright for a fixed or solid-colour sky. There is also an
[editor](./sky-grades#the-editor) for authoring them.

| 0.5                                                   | 0.6                                                                                                                                      |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `sky.setLook({ stops, chroma, value, sunTint })`      | `sky.setGrade(gradientGrade(stops, { amount: chroma, replace: value }))`; a `sunTint` becomes the `sunward` / `glow` zones of a keyframe |
| `sky.setLook('ghibli-day')`, `setLookTrack('ghibli')` | `sky.setGrade('storybook')` — or author your own in the editor                                                                           |
| `setLookTrack([{ elevation, look }, …])`              | `new SkyGrade([{ elevation, gradient: { stops, amount, replace } }, …])`                                                                 |
| look stop `at`: sin(elevation), −1…1                  | gradient stop `at`: elevation in **degrees**, −90…90 (`asin(at) × 180 / π`)                                                              |
| look stop `ease: 1.8`                                 | the same (`'linear'`, `'smooth'` or a number)                                                                                            |
| `intensity`                                           | scale the stop colours, or the keyframe's `exposure`                                                                                     |
| `registerLook` / `registerLookTrack`                  | `registerGrade(name, grade)`                                                                                                             |
| `setLook(null)` / `setLookTrack(null)`                | `setGrade(null)`                                                                                                                         |
| React `look`, `lookTrack`, `lookTrackOverrides`       | React `grade`                                                                                                                            |
| `baker.sky.lookUniforms.displayScale`                 | `baker.sky.displayScale`                                                                                                                 |
| `createHazeOutputNode({ lookUniforms })`              | `createHazeOutputNode({ gradeUniforms: baker.sky.gradeUniforms })` (`applyHaze` wires it for you)                                        |

A look's `value` axis pulled the sky's brightness toward the ramp's; a
gradient's `replace` mixes the gradient in whole, colour and brightness, which
is close at low values and exact at 1. A look at `chroma: 1, value: 0` maps to
`amount: 1, replace: 0` exactly in hue, but keeps the channel average rather
than the luminance, so saturated blues read deeper than before.

`ColorInput` is still exported.

## 0.4 → 0.5: three r186 or later

0.5 needs `three` 0.186 or later (0.4 ran on r185). Upgrade three alongside it:

```sh
npm install three@^0.186.1 @pmndrs/sky
```

The sky itself renders the same on r186. Lit objects in your scene may not:
r186 reworked three's own shading (the GGX specular and its lookup table, the
environment lighting and shadow filtering), so rough, sunlit surfaces can come
out a little darker. r186 also removed `PCFSoftShadowMap`; three falls back to
`PCFShadowMap` with a console warning.

### No shader compiles on the first frame: await `compileAsync()`

0.5 compiles every shader the sky needs in the background, starting when the
sky is constructed, and on WebGPU it no longer uses three's `PMREMGenerator`
at all: its own compute prefilter allocates the IBL texture and fills it. Add
one line before your render loop:

```js
await renderer.init()
const sky = new Sky(renderer, { timeOfDay: 16 })
sky.attach(scene)
await sky.compileAsync() // new
renderer.setAnimationLoop(frame)
```

The React `<Sky>` does this for you. If you skip it, nothing breaks: `update()`
skips its bakes until the shaders are ready and logs one warning, so **the sky
and its lighting appear a few frames late** instead of on the first frame. 0.4
compiled them synchronously inside the first `update()` instead, which could
freeze that frame for a second or more on Windows.

Smaller changes:

- `sky.baker.environmentTexture` (and `scene.environment` after `attach()`)
  exists from construction, where 0.4 returned `null` until the first bake.
  It is still the same texture object for the sky's lifetime.
- The background cube's mip chain is filled by the sky's compute pass, not
  by three. If you set `generateMipmaps` on `baker.texture` yourself, leave it
  as the sky sets it.
- `baker.pmremGenerator` is created only when it is used (WebGL, or
  `pmrem: { generator: 'three' }`). `pmrem: { generator: 'three' }` keeps 0.4's
  behaviour, synchronous first bake included.

## 0.3 → 0.4 at a glance

Check these against your project. Each links to the details below.

- **Every scene:** the sky is brighter, and the default ground albedo is now
  `0.1` (was `0.3`). [Details](#the-sky-is-brighter,-and-noon-no-longer-whites-out)
- **Every scene with a sun from `timeOfDay`:** the sun now rises in the east.
  0.3 had the compass mirrored, so the sun crosses to the other side of the
  north–south line. [Details](#east-is-on-the-right:-the-compass-was-mirrored)
- **`setSunDirection({ elevation, azimuth })`:** a compass azimuth now lands on
  the mirrored side. Pass `360 - azimuth` to keep a hand-placed sun where it
  was. [Details](#east-is-on-the-right:-the-compass-was-mirrored)
- **`createSun()`:** the light goes out once the sun has set, and
  `sun.intensity` is the requested value, not the effective one.
  [Details](#skysun-goes-dark-when-the-sun-sets)
- **Stars:** the 0.3 star API (`setStarsDensity`, `setStarsBrightness`,
  `setStarsRotation`, `setStarsSource`, `source: 'hdri'`) is gone.
  [Details](#stars:-new-api,-old-calls-removed)
- **Custom looks with `value > 0`:** multiply `intensity` by your
  `toneMappingExposure` to keep the 0.3 result. [Details](#looks:-ramp-intensity-is-display-referred)
- **A live sky mesh (`createSkyMesh`) or your own `SkyAtmosphereMesh`:** it
  now draws after opaque geometry without writing depth.
  [Details](#the-live-sky-mesh-draws-after-opaque-geometry)
- **Haze with the camera above about 1 km:** a per-pixel refinement removes
  the old concentric bands and costs about 0.5–2 ms there.
  `apRefineSteps: 0` turns it off. [Details](#haze-is-more-accurate-near-the-camera-and-from-altitude)
- **Exposure animated per frame** (`setExposure` or
  `renderer.toneMappingExposure`): each change now re-bakes the background
  and IBL. [Details](#setexposure-updates-the-background-and-reflections)
- **`setTurbidity` called with ratios:** it is absolute now.
  [Details](#setturbidity-is-absolute)

The rest are fixes you get without changing anything, or opt-in features.

## The sky is brighter, and noon no longer whites out

Matching Bruneton's reference sky fixed several things at once: the Sky-View
LUT samples the horizon more finely, the haze sky mask and ray precision were
fixed, and the default **ground albedo dropped from 0.3 to 0.1**. The sky is
brighter overall, by about 15%, and by up to about 40% near a low sun. The
noon whiteout some scenes had is gone.

- If you tuned `toneMappingExposure` or the sky's exposure around the old,
  dimmer sky, check it again.
- To keep the old ground bounce, pass it explicitly:
  `new Sky(renderer, { groundAlbedo: 0.3 })`. Expect a bright band along the
  horizon with it; see [`groundAlbedo`](./tuning-atmosphere#groundalbedo).

## East is on the right: the compass was mirrored

Compass azimuths turned the wrong way in 0.3: with the default `north: '+Z'`,
an azimuth of 90° (east) landed on +X, which is on your _left_ when you face
+Z. The morning sun therefore rose in the west, and the star field was
mirrored the same way. Azimuths now turn clockwise seen from above, as on a
map: facing north, east is on your right, so with `north: '+Z'` east is −X.

- Scenes driven by `timeOfDay` see the sun on the other side of the
  north–south line at the same hour: a morning sun that used to sit on +X now
  sits on −X. Noon and the sun's elevation are unchanged. If you had worked
  around the mirrored sun (by flipping `north` or the scene), remove the
  workaround.
- A sun placed with `setSunDirection({ elevation, azimuth })` moves to the
  mirrored azimuth. To keep its old position, pass `360 - azimuth`. That
  holds for every `north` axis.
- Sun directions set with `raw: true` never went through the compass and are
  unchanged.
- `SkyMoon.setDirection` now applies `north` as its docs said, and turns
  with `setNorth`.

`north` also accepts any heading in degrees now, so a site plan's north arrow
can be matched exactly; see [Compass](../api/sky#compass).

## `SkySun` goes dark when the sun sets

A `createSun()` light used to keep its full intensity with the sun below the
horizon, lighting the scene from underneath at night. It now fades with the
fraction of the sun's disc above the horizon, over one disc diameter (~0.53°),
and is off once the disc has set. Every sun path applies it: `setTimeOfDay`,
`setSunDirection`, latitude, date and north, and a light created at night
starts dark.

`sun.intensity` is now the **requested** daytime intensity and stays at what
you set, at night too; `sun.light.intensity` is the effective value. So:

- Delete any workaround that scaled `sun.light.intensity` by the sun's
  elevation; set `sun.intensity` (or `sun.setIntensity(v)`) once.
- Code that read `sun.intensity` to get the scene's current light value
  should read `sun.light.intensity`.
- Values written straight to `sun.light.intensity` last only until the next
  sun change. To drive the intensity yourself (a wider, stylised ramp, or
  deliberate light from below the horizon), pass `horizonFade: false` or call
  `sun.setHorizonFade(false)`.

New and opt-in: `createSun({ physical: true })` derives the light's intensity
and colour from the sky (`exposure × T(sun)`), which is about 9× brighter than
the default `4` at noon; see [`createSun`](../api/sky#skysun).

## Stars: new API, old calls removed

0.3 baked a procedural starfield (or an HDRI) into the sky cube, which is what
made the stars blurry. 0.4 draws them as sprites in your scene and bakes only
the Milky Way's glow. The stars are placed from `timeOfDay`, `dayOfYear`,
`latitude` and `north`, so they turn with the sky on their own.

`sky.enableStars()`, `disableStars()`, `setStarsIntensity()` and `sky.stars`
work as before. The rest of the 0.3 star API was removed: a removed method
throws when called, and a removed option is ignored, so an old
`enableStars({ density: 2 })` still runs, with the defaults.

| 0.3                                                                     | 0.4                                                                                |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `setStarsDensity(n)`, `{ density }`                                     | `{ count }` (number of procedural stars)                                           |
| `setStarsBrightness(n)`, `{ brightness }`                               | `setStarsIntensity(n)`, `{ intensity }`                                            |
| `setStarsRotation(r)`, `{ rotation }`                                   | Nothing to do: the sky follows the time, date, latitude and `north`.               |
| `setStarsSource(s)`, `{ source, url }`                                  | Load the map yourself (galactic coordinates) and pass it as `{ milkyWayTexture }`. |
| `{ texture }`                                                           | `{ milkyWayTexture }`, if the map is in galactic coordinates                       |
| `SkyNight` `setDensity` / `setBrightness` / `setRotation` / `setSource` | `setIntensity`, `setSize`, `setContrast`, `setMilkyWay`, … (see the guide)         |

See [Night sky](./night-sky) for the new options.

## Reflections update every frame (and look slightly different on three r185/r186)

On the WebGPU backend, the environment map (`sky.environmentTexture`, the
image-based lighting for `scene.environment`) is now re-filtered with compute
shaders on every sky change, in the same frame as the background. Before, it
was refreshed at most every 250 ms and spread over several frames, so
reflections lagged a moving sun. It costs about 1 ms per change at the default
256 cube. See [the PMREM section of the baker docs](<../api/baker#environment-(pmrem)-refresh>).

- **three r187+:** the output is identical to three's `PMREMGenerator`.
- **three r185/r186:** three's generator doesn't filter its levels at the
  roughness its own material sampler expects. Ours does, which is about 7×
  closer to the true GGX reflection. Rough metals therefore reflect a softer
  horizon, and very rough surfaces keep the ground's falloff.
- **WebGL backend:** unchanged; there's no compute, so three's generator is
  used as before.

To get the old generator and look back:

```js
new Sky(renderer, { pmrem: { generator: 'three' } })
```

`environmentTexture` is still the same texture object from the first bake to
`dispose()`, so materials don't recompile.

## `setExposure` updates the background and reflections

In 0.3, `setExposure(n)` (and the React `exposure` prop) only changed the
live sky mesh. The baked background and the IBL kept the old exposure until
something else re-baked them. Now a change re-bakes the cube and IBL, so
everything matches straight away. Setting the same value again costs
nothing, but animating the exposure now costs a cube + IBL bake on every
frame it changes (about 1 ms with the default compute IBL). The same goes for
`renderer.toneMappingExposure`, which `Sky.update()` feeds to the
[looks](#looks:-ramp-intensity-is-display-referred).

## The live sky mesh draws after opaque geometry

This only affects the live sky mesh from `baker.createSkyMesh()` (used by the
planet-scale setups) and a `SkyAtmosphereMesh` you add yourself; `Sky`'s
default background is the baked cube and is unchanged. The live sky now draws
like a game-engine sky: after the opaque geometry, depth-tested at the far
plane, without writing depth. Sky hidden behind geometry is never shaded,
which is faster, and transparent objects still draw over it.

If you create your own `SkyAtmosphereMesh`, give it the same order:

```js
import { SKY_RENDER_ORDER } from '@pmndrs/sky'

mesh.renderOrder = SKY_RENDER_ORDER
```

If you relied on the sky drawing first (`renderOrder = -1` in 0.3), for
example to draw something behind it, move that object to a lower
`renderOrder` than `SKY_RENDER_ORDER` and give it depth. An opaque object
that doesn't write depth (`depthWrite: false`) is now painted over by the
sky; draw it as transparent, or let it write depth.

## Haze is more accurate near the camera and from altitude

Three fixes change how aerial-perspective haze looks; none needs code changes.

- **Near the camera.** The haze volume now uses Hillaire's per-slice step
  counts, covering each slice's whole ray. It used to read 2–3 % too thin,
  and up to 5–7 % in the far slices. Final frames move by two or three 8-bit
  steps at most.
- **From altitude.** Above about 1 km camera altitude, each pixel refines the
  depth-slice lookup with a short march of its own, which removes the faint
  concentric rings the slices left on the ground seen from above. It costs
  nothing at ground level, about 0.55 ms at 25 km and 1–2 ms at 75 km
  (1080p, ground filling the screen). To get the 0.3 cost back, pass
  `apRefineSteps: 0` to `applyHaze` (or `<AutoHaze>`); see
  [Haze seen from altitude](<./haze#haze-seen-from-altitude-(slice-refinement)>).
- **From space.** With the camera above the atmosphere and `policy: 'ap'`,
  the volume used to hold haze for stretches of the ray still in vacuum, and
  the ground looked washed out. It now starts where the ray enters the
  atmosphere. The default `'auto'` policy raymarches up there and is
  unchanged.

## `setTurbidity` is absolute

`setTurbidity(n)` now sets the haze relative to turbidity 1. Before, each call
scaled relative to the previous value, so repeated calls compounded, and a
value of 0 could never be recovered from. `setPreset(...)`, or Mie fields
passed to `setAtmosphere(...)`, reset the turbidity-1 baseline.

If you called `setTurbidity` with ratios to step the haze, pass the absolute
value you want instead.

## Looks: ramp intensity is display-referred

A look's colour ramp is now multiplied by `1 / renderer.toneMappingExposure`,
which `Sky.update()` keeps in sync, so at `value: 1` the authored colours
reach the screen as authored, whatever the sky's exposure. Looks with
`value: 0` (chroma only) are unaffected. The built-in Ghibli palettes were
retuned. (Looks were replaced by sky grades in 0.6; see
[0.5 → 0.6](#0.5-→-0.6:-looks-are-replaced-by-sky-grades).)

Custom looks that use `value > 0` and were tuned against 0.3 render
differently. To get exactly the 0.3 result, multiply the look's `intensity`
by your `toneMappingExposure` (with `toneMappingExposure: 0.5`, an
`intensity` of 1 becomes 0.5).

A look's `sunTint` also changed shape with the sun high: it used to tint
every view toward the sun's azimuth, from the horizon to the zenith, and is
now a round glow around the sun from about 30° up. Sunsets look the same.

If you drive `SkyAtmosphereBaker` directly instead of `Sky`, keep the
display scale in sync with the exposure yourself (`baker.sky.displayScale`
since 0.6; see the [baker docs](../api/baker#keeping-the-grade-display-referred)).

## Sun colour, and `SkySun` follows it

`sunColor` (an option and `setSunColor('neutral' | 'bruneton' | color)`) tints
the sky, haze, sun disc and `createSun()` lights together. The default is a
white sun, as before.

A `SkySun` light's colour is now `baseColor × the sky's sun colour`, so the
next `setSunColor` (or sun move) overwrites anything assigned to
`sun.light.color` directly.
Set your colour with `sun.setColor(...)` instead.

## Haze setters work before `applyHaze`

`setHazeStrength`, `setHazePolicy`, `setHazeAltitudeBlend` and the new
`setHazeShadows` can be called before `applyHaze()`; `applyHaze()` adopts the
current values. Before, they were silently ignored until haze was wired, so
code that set them first and wired haze later now gets the values it asked
for.

## `attach()` can leave `scene.environment` (or the background) alone

`sky.attach(scene, { environment: false })` shows the sky as the background
and keeps your own environment map; `{ background: false }` does the reverse.
Stars attach either way. React has matching `background` / `environment`
props. See [Attach roles](../api/sky#attach-roles).

One change for the default `attach(scene)`: `update()` used to put the sky's
IBL back into `scene.environment` every frame, overwriting anything assigned
after `attach()`. It now only fills the slot while it is empty or still holds
the sky's texture, so an environment you assign later stays. To hand the slot
back to the sky, call `attach(scene)` again.

## `quality: 'low'` and `'high'` are sampled correctly

The `'low'` and `'high'` tiers (and any custom `lutResolutions`) allocated
differently sized LUTs, but the lookups still assumed the `'medium'` sizes,
so those skies were sampled slightly off. Every lookup now uses the size of
the texture it reads. `'medium'` (the default) is unchanged; a `'low'` or
`'high'` sky may shift slightly. See [LUTs](../api/luts#resolutions-/-lut_resolutions).

## React

- **Object props compare by value.** `<Sky>` props such as `sunDirection`,
  `groundAlbedo`, `atmosphere` or colours are compared by value, so writing
  them inline (a new object every render) no longer re-bakes the sky every
  render. Nothing to change; inline objects are fine now.
- **`turbidity` applies on top of `atmosphere`**, and again whenever
  `atmosphere` changes, so the two props no longer fight over the Mie values.
- **Removing `lookTrack` clears the track**: the sky falls back to `look`, or
  to the physical sky. Before, the track stayed on.
- New props: `background`, `environment`, `pmrem`, `sunColor`, `fog`,
  `lookTrackOverrides`, and `north` in degrees. `<AutoHaze mode="fog" />`
  wires height fog instead of haze. `SkyProps` and `SkyContextValue` are
  exported as types. See the [React reference](../api/react).

## Deprecated atmosphere fields

The `ozone*` and `sunIlluminance` fields of the atmosphere params are
`@deprecated`: no shader reads them, so setting them has no effect.
`sunAngularRadius` now resizes the sun disc.

## `update()` inside a G-buffer frame

`sky.update()` called while your own MRT was set (`renderer.setMRT(...)`)
compiled the sky bake under it and failed with WebGPU validation errors every
frame. Internal draws now clear the MRT and restore your renderer state
afterwards, even if a draw throws. If you cleared the MRT around
`sky.update()` as a workaround, you can drop it. See
[Renderer state](../api/baker#renderer-state).

## three.js r187

0.3 failed to load against three's unreleased r187 (`dev`), because it
imported an export r187 removed. 0.4 loads on it, and the per-frame IBL
supports both PMREM formats: r185/r186's CubeUV atlas and r187's cube mips.
CI tested against r185 then; from 0.5 it tests r186.
